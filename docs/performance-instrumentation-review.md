# Performance instrumentation review

PR #30 includes the worker-row layout fix and the five instrumentation/adaptive-quality fixes. Solver equations, constraint order, cloth settings, timestep policy, and authored scene visuals are unchanged. Adaptive resolution now changes only for rendering pressure.

## Fix notes

1. **Adaptive resolution.** Cause: the previous decision used display FPS alone, which cannot identify CPU pressure. WebGL now polls `EXT_disjoint_timer_query_webgl2` without waiting; WebGPU requests supported `timestamp-query` and resolves render/compute pass timestamps asynchronously. Stale query generations and WebGL disjoint results are discarded. CPU-bound frames hold resolution; GPU compute pressure alone also holds it. Rendering overload can reduce resolution, and headroom permits recovery. Without timestamps, main-thread work at or above 70% of the frame interval holds resolution. Both captured backends held 1.0. GPU values are pass execution durations, not end-to-end completion latency.

2. **Warm-up and configuration windows.** Cause: player profiling was lifetime-based, and the rolling frame window survived settings changes, so old and new configurations could mix. Load, setting/reset, population changes, focus/visibility restoration, and canvas resize now restart observations and exclude three seconds. Reports print the duration and excluded frame count (143 WebGL, 187 WebGPU in these captures). Neither baseline nor updated steady-state capture contained a frame at or above 50 ms; this is consistent with a transition spike, but does not prove the cause of the user's earlier screenshot. Later stalls remain in the statistics, with the old 250 ms clamp removed; a regression test retains a real 300 ms stall.

3. **Player step timings.** Cause: the old report mixed lifetime sparse awake-step samples with current per-callback main-thread physics, which also includes controllers, worker scheduling/result reconciliation, and geometry sync. Sampling now covers awake steps in the last fifteen seconds at 1/16; fewer than thirty samples prints `insufficient samples`. Timers remain coarse phase boundaries, including repeated solver passes, never particles or constraints. Unattributed step overhead is included in finalization so phases sum to the step total. The WebGL capture has ninety player samples, 4.57 ms/awake step with a 4.57 ms phase sum. Its 15.71 ms main-thread physics/callback has a broader scope; the copied report explains why multiplying player step time by all steps/callback is not that total.

4. **Worker budget.** Existing policy already reserved two logical cores, capped at ten workers, with minimum one and unknown-core fallback four. The policy is retained and now visible alongside logical cores, chosen workers, and assignments. Tests explicitly emulate four reported threads: two workers, fifty assigned capes, and 1,200 overloaded callbacks retain at most one queued batch per worker and dispatch the freshest pose. This proves queue bounds, not the absence of main-thread starvation on a physical four-thread machine; that hardware measurement remains unavailable.

5. **Worker and workload reporting.** The former `MS/STEP` was elapsed execution time around a worker's assigned-cape solve/input-update loop, excluding result packing and message waits; it was not simulated timestep. Compute, simulated DT, delivered rate, solve-wall utilization, per-worker cape/particle assignment, worker ms/s, main physics ms/s, and actual CPU particle delivery are now distinct. The panel's main scope hint includes player/controllers/sync; the report also names worker reconciliation. Constraint types and browser device-memory approximation are report-only. On this machine each worker solves five capes / 1,170 particles; the WebGL capture averages 23.93 ms compute, 28.76 ms simulated DT, and 66.9% solve-wall utilization (6,688.58 ms/s summed). Workers were not near saturation in that window. Body collision, self collision, reconciliation, and cave collision account for much of sampled awake-step cost; the report contains every worker's phase breakdown and 2,062 colliders/cape. Elapsed solve timers can include OS preemption, so utilization is not an OS CPU counter.

During fullscreen/resize warm-up, the HUD retains its previous values and graph, dims them, and labels them `WARMING UP / PREVIOUS STATS` until fresh frame samples arrive. Repeated resize events retain the same display; measurement windows and copied reports still reset and contain no previous samples. Numeric values in particle, constraint, worker, throughput, and hardware rows use the same brighter bold style as the original FPS and timing values. The follow-up passed fourteen focused tests, TypeScript checking, and a production build.

The worker HUD uses four explicit non-wrapping lines with reserved height and tabular numerals, separating compute/rate, timestep/utilization, and assignments. Number updates cannot add a wrapped line. Existing ANGLE identification, hardware fields, particle/constraint totals, and the Timing caveat are retained.

## Validation and limitations

- Full repository check: 260 passed, six existing stress tests skipped, zero failures; production build passed.
- Final targeted check after label/accounting changes: 26 passed, zero failures; TypeScript and source-size budgets passed. Four-thread parameterization adds one test relative to the full run.
- Both backend report captures exercised actual NVIDIA rendering and measured GPU timestamps. WebGL capture cleanup succeeded.
- Windows rejected removal of several dedicated WebGPU audit profiles under `artifacts/.tmp/` with EPERM. Cleanup errors were surfaced as failures; these runs are not marked clean successes. No further browser retries were performed. The capture utility keeps temporary data on G:, cleans in finally, and preserves primary capture errors before reporting cleanup errors. No physical four-thread benchmark or final clean WebGPU recapture is claimed.
